**Selected function/component:** `recommend()` route of the model server — [`cornac/serving/app.py#L120-L150`](https://github.com/anstieger/cornac/blob/0d4efe3cf6ddfe3f99827f30d9dab5f35d625d69/cornac/serving/app.py#L120-L150), which calls the library method [`Recommender.recommend()`](https://github.com/anstieger/cornac/blob/0d4efe3cf6ddfe3f99827f30d9dab5f35d625d69/cornac/models/recommender.py#L532-L580).  

**Why this represents the software's purpose:** Cornac exists to produce item recommendations for users; the server is the part that delivers them to an application. A request goes through the whole path a client uses: loading a saved model and its train set, ID mapping, scoring/ranking by the model and filtering of seen items.  

**Representative input and baseline expectation:** BPR (`k=10, max_iter=100, lr=0.01, λ=0.01, seed=123`) trained on the repository fixture `tests/data.txt` (10 users × 10 items, one interaction each — the same model the upstream serving test uses), saved with its train set and served by `flask --app cornac.serving.app`. Request: `GET /recommend?uid=930&k=-1`. User 930 has already interacted with item `709`. 
**Baseline (documented default `remove_seen=false`):** all 10 items are returned, `709` included, and `query.remove_seen` is `false` — identical to the response for an explicit `remove_seen=false`.  

**Planned small behavior change:** When the server has the train set loaded, `/recommend` removes the items the user already interacted with **by default**, i.e. the same request returns 9 items without `709` and `query.remove_seen=true`. Reason: re-recommending something the user has already consumed is rarely wanted (this is the handout's own example rule), and the server already has the information but used it only if the client knew the extra parameter. Clients can still get the old list with `remove_seen=false`; without a train set the default stays `false` (no new error).  

**What must still work unchanged?** Explicit `remove_seen=false` returns all 10 items incl. `709`; explicit `remove_seen=true` returns exactly that list without `709`, same order (the ranking itself is not touched); `k=5` returns 5 items; all requests return 200; the library method `Recommender.recommend()` is unchanged (upstream test `tests/cornac/models/test_recommender.py::TestRecommender::test_recommend`).

**Reused upstream tests (existing in the Cornac repository):**
- [`tests/cornac/serving/test_app.py`](https://github.com/anstieger/cornac/blob/0d4efe3cf6ddfe3f99827f30d9dab5f35d625d69/tests/cornac/serving/test_app.py) — already tests this endpoint with the same fixture (BPR on `tests/data.txt`, saved with train set, Flask test client). Reused as-is: `test_create_app`, `test_recommend`, the `/feedback` and `/evaluate` tests and the fixtures. `test_recommend` already asserted `query.remove_seen == False`, i.e. the old default — this is the upstream expectation that the change makes obsolete. Added by me (Lab 7): `test_recommend_explicit_remove_seen_unchanged` (invariant) and `test_recommend_default_seen_items` (contract).
- [`tests/cornac/models/test_recommender.py`](https://github.com/anstieger/cornac/blob/0d4efe3cf6ddfe3f99827f30d9dab5f35d625d69/tests/cornac/models/test_recommender.py) — `TestRecommender::test_recommend` checks that `remove_seen=True` changes the library output. Reused unchanged as library-level regression check.

**How do your checks distinguish the two versions?** For the same request, `lab7_serve_check.py` always evaluates both contracts and prints which one holds: OLD = default response equals the `remove_seen=false` response and reports `remove_seen:false`; NEW = default response equals the `remove_seen=true` response, reports `remove_seen:true` and contains no seen item (also for `k=5`). The commit states which contract it promises (`EXPECTED_DEFAULT_REMOVE_SEEN`) and the job fails if that one does not hold. The invariant checks compare explicit requests that must give the same answer in both versions, so the new version is not accepted just because expectations were rewritten. The intermediate run C1a (new code, old expectations) shows that the pipeline actually detects the change: In run C1a the functional check reported `OLD contract no`, `NEW contract HOLDS`, all 5 invariants PASS, and failed because the commit still promised the old default (`expected_default_remove_seen: false`). pytest in the same run: **2 failed, 20 passed** — exactly the two tests that encode the old default: upstream `test_recommend` (`assert response.json['query']['remove_seen'] == False` → `assert True == False`) and `test_recommend_default_seen_items` (default list ≠ `remove_seen=false` list: `'709'` missing at index 1). The unchanged checks `test_recommend_explicit_remove_seen_unchanged` and `test_recommender.py::test_recommend` passed. The log also printed the deployed source line `app.py:133 default_remove_seen = "true" if train_set is not None else "false"`, so the red result is tied to the new code, not to a test edit (C1a changes only `cornac/serving/app.py`). C1a build+install 384 s, server ready 1085 ms.

**Did anything fail unexpectedly? What did you learn or fix?** No unexpected test failure; the only red run (C1a) was the planned one and failed exactly in the two old-default checks. Two practical issues: (1) my first push of C1a was rejected with HTTP 403 because git on my laptop was logged in with a different GitHub account than the fork owner — fixed by using the `anstieger` account for the remote; the commit itself was unchanged. (2) The runs did not all use the same runner image: baseline and C1a ran on image version `20261111.635`, C1b on `20261116.376.1` (GitHub updated `ubuntu-24.04` in between). Python 3.12.16, Cython 3.3.2, numpy 2.5.5, scipy 1.18.1 and Flask 3.1.3 were the same and the `remove_seen=false` ranking was identical in all three runs, so the image update did not affect the result — but it shows that `ubuntu-24.04` and unpinned `pip install` are not a fixed environment. Timing per run: build+install 394 / 384 / 406 s, server ready 1055 / 1085 / 2027 ms (baseline / C1a / C1b), i.e. the deployment cost is dominated by compiling the Cython extensions.

## 4. Engineering judgment and submission

**Answer Q1:** Yes. In all three runs the job checked out exactly the pushed SHA (`GITHUB_SHA` = `HEAD`: `0d4efe3c`, `e1246f7e`, `f5bfec9b`), compiled Cornac from that checkout in 384–406 s, loaded `cornac` 3.0.1 and `cornac.serving.app` from `/home/runner/work/cornac/cornac/…` (the workspace, not PyPI) and the server answered every request with HTTP 200 after 1–2 s. The deployed `remove_seen` source line printed by the job changes from `app.py:130 … "false"` (baseline) to `app.py:133-134 default_remove_seen = "true" if train_set …` (C1a/C1b), which ties each observed behavior to the code that was deployed.

**Answer Q2:** Yes. For the same request the baseline returned 10 items with the seen item `709` at rank 2 (OLD contract), the changed version 9 items without `709`, the other items in the same order (NEW contract). With the new code but the old expectations (C1a) the pipeline turned red in exactly the contract checks — the functional check and 2 of 22 tests, one of them the upstream `test_recommend` — while all 5 invariants and the unchanged tests stayed green. After updating the expectations (C1b) the functional check and 22/22 tests passed. The `remove_seen=false` response was identical in all three runs, so the change is visible and the unchanged behavior is still verified.

**Release decision:** **Accept the changed version**, with a release note: the behavior was executed from the intended commit and verified, the unchanged explicit-parameter behavior is confirmed, and the ranking itself is untouched. Because it changes a public API default, it should be announced as a behavior change (clients that relied on seen items must now send `remove_seen=false`).  
**One important limitation or missing check:** The experiment uses one tiny fixture model and one user with a single seen item, on Flask's development server; it does not check the path where no train set is loaded (default must stay `false`) nor a production WSGI setup, and it says nothing about recommendation quality.
